What ARC-1 should adopt from ADT for VS Code 1.2

Build on ARC-1’s existing operations. The best new work is a reusable SQL notebook experience, caller-specific explanations of policy decisions, and richer diagnostic feed filters. Much of the apparent feature gap is already closed in the released code or pending 1.6.0.

Access controls: keep the engine, improve the explanation

SAP’s controls distinguish project/destination access from package-level creation and modification. Reads are not restricted by the package list. ARC-1 already implements this separation and adds functional scopes, independent capability gates and action denials. These mechanisms have different purposes and should stay distinct. SAP configuration reference; ARC-1 safety implementation.

1. Destination restrictions are already being delivered

PR #677 merged October 14. In the opt-in xsuaa-attribute mode, verified XSUAA user attributes contain exact public target IDs such as QAS/001. A literal * is an explicit all-target grant; partial wildcards are not supported. The same grant applies to discovery, aggregate calls and pinned routes. Admin diagnostic visibility is not an execution grant.

Recommendation: validate and release this implementation for 1.6.0. Do not describe it as available in published 1.5.2. Preserve standard behavior for existing deployments; enable filtering only through the documented rollout. The mode remains mutation-free. The open pinned-writes PR #906 is a separate proposal, not an adopted expansion of this boundary. ADR-0008.

2. Package restrictions are a preservation task

Keep SAP_ALLOWED_PACKAGES as a write restriction. ARC-1 resolves the real package of an existing object before applying the rule; a supplied package name is not sufficient. Exact, prefix and subtree rules already serve useful deployment needs. Package movement needs the existing source/destination checks, and activation remains a guarded operation. Package enforcement.

Do not reuse that setting to hide source or filter SQL data. Reads are intentionally not package-gated; data-preview/SQL controls and the optional data-source blocklist are separate. The blocklist is also not a general business-data authorization model. Per-user package grants would be another policy dimension: defer them until there is a concrete multi-user authoring requirement, then intersect them with the server ceiling rather than overriding it.

3. Add a caller-specific policy explanation

Proposed interface, not an existing tool: SAPManage(action="policy_explain", operation=…). A summary should answer “Can this caller query data, edit this object, or release this request through this ARC-1 route?” without trying the mutation. Reuse the authorization and safety evaluators; do not maintain a parallel list of rules in the UI.

{
  "operation": "SAPWrite.update",
  "object": {"type": "CLAS", "name": "ZCL_DEMO"},
  "arc1Decision": "denied",
  "reasonCode": "PACKAGE_NOT_ALLOWED",
  "sapAuthorization": "not_checked"
}

This is an illustrative response contract. It must distinguish denied, permitted by ARC-1 policy, and unknown. Resolving object metadata may require a read under the caller’s SAP identity; a failure is not permission. Do not return hidden target inventories, raw entitlement arrays, secrets or other users’ policy. Adjust ACTION_POLICY so a safe self-view is accessible without granting admin rights; operator-only detail stays in the existing admin console.

Acceptance: explanation agrees with runtime denials for representative scope/flag/package/target combinations; no mutation is sent; current state is rechecked on actual execution; unknown and ungranted target requests do not reveal inventory. The existing admin UI overview and effective-policy logging should be reused, not replaced.

SQL notebooks: the strongest visible addition

The useful idea is to make an investigation reproducible: explanation, query, target, limits and observed results stay together. SAP’s notebook supplies Markdown/code cells, execution, statistics and exports. ARC-1 already has the execution foundation. SAP notebook documentation; SAPQuery handler.

Stage A: reusable artifacts before a new editor

Publish a small notebook recipe and import/export library with the flight example, plus useful investigation examples such as data-quality counts and bounded reconciliation. Persist Markdown and ABAP SQL with a format version. Keep target aliases separate from credentials. Provide an .abapsql compatibility adapter tested against SAP 1.2; treat the observed file structure as a versioned integration, not a promised SAP public interchange standard.

Export a static HTML report and optional CSV after execution, recording the executed query, selected target, capture time, returned row count, limits and backend timing. Result snapshots should be an explicit save choice. The recipe can be shared without embedding a customer’s business data. An HTML export must escape returned text, and CSV needs a spreadsheet-formula safety policy.

Stage B: a thin client runner

Use the existing MCP SAPQuery call for every SQL cell. A small VS Code companion is a practical first client: the public Notebook API separates serializer, controller and renderer. A Werkbank presentation can reuse the same artifact/runner contract later if desired. Do not add a second SAP connection stack or execute around ARC-1’s policy checks. VS Code Notebook API.

  1. The client opens cells and resolves the chosen ARC-1 connection or authorized target explicitly. Opening/importing a document never executes it.
  2. A cell calls SAPQuery with its SQL and bounded maxRows. A structured table cell can instead use SAPRead(type="TABLE_QUERY") under its existing data-preview policy; it must not be used to bypass free-SQL restrictions.
  3. The renderer displays returned columns and string values faithfully. Preserve leading zeros, decimals and large numeric identifiers. Only generate charts when the user selects compatible columns.
  4. Run All executes sequentially initially. Cancel stops queued work and cancels the client request where supported; do not promise that this kills an already-running SAP database statement.
  5. Switching targets invalidates or clearly marks earlier outputs. Never silently reroute a failed query to another system.

Keep ARC-1’s limits: default 100 rows, current 10,000-row clamp, cumulative response-byte budget and data-result concurrency cap. SAP’s notebook documents a 100,000 maximum, but that is not a reason to increase a shared gateway’s limits. Show incomplete/limited results explicitly; do not promise a complete dataset merely because a grid rendered. Row clamp; Response-budget implementation.

Scope boundary: the existing ARC-1 browser console is an operator inspection UI, not an end-user query workbench. Do not quietly add query execution to its admin routes or enable it in multi-target mode. MCP Apps could be a later optional renderer, after validating client support and ARC-1’s protocol constraints; notebooks do not require a protocol migration. No Python/Jupyter runtime is necessary.

Acceptance: replay the flight notebook on an authorized 7.58 instance through ARC-1; match the existing six-carrier result; verify denied SQL stays denied; test UTF-8, leading zeros, escaped result text, saved/reopened cells, missing target, login expiry, row/byte limits and partial Run All failure. Test source-only export separately from result export. An unavailable syntax-check endpoint must not be simulated by silently executing the query.

Diagnostics: adopt backend discovery and precise filters

Feed filters and schema discovery

ARC-1 already reads dumps, Gateway errors and system messages. The gap is asking precise questions such as “TIME_OUT errors for this application during the last hour” without fetching a broad feed. Existing FEAT-74 records real feed-schema and filter evidence on 8.16. I recommend promoting it from P3 to P1 for the first bounded slice.

Add a read-only feed-schema operation under SAPDiagnose and optional typed filter inputs to the existing actions. Discover supported attributes and operators from the selected backend’s /sap/bc/adt/feeds metadata. Compile a small filter tree with bounds on depth, conditions and value length; serialize according to the verified wire contract. Preserve user/from/to compatibility.

A specific compatibility trap: SAP’s current VS Code UI documentation uses quoted values and ISO-style date/time formats, while ARC-1’s recorded backend examples use a different representation. A UI expression is not automatically the raw ADT wire expression. Keep logical filters independent of serialization and verify both 7.58 and 8.16. Follow known paging behavior rather than blindly replaying next links that accumulate client parameters. SAP feed documentation.

Return bounded entries plus filter/schema provenance, continuation and explicit truncation. Do not infer an automatic monitor from a manually refreshed feed. Extend to ATC and Unit-run feeds only when the backend advertises them and their contracts are verified; running a new ATC check and reading a historical feed are different operations.

Acceptance: unsupported attributes fail clearly; hostile strings remain data; direct and paged results agree for a bounded fixture; 403/404 are distinguished; per-user/target context is preserved. Treat feed details as potentially sensitive, especially Gateway payloads, and avoid copying full entries into broad audit logs.

Dictionary activation logs

Promote FEAT-71 to a P2 investigation, not an implementation promise. Current research says the resource is not a simple GET. Capture the exact request and response sequence for a controlled test-object failure using normal ADT; establish lifetime, object association, content types and release support. This review did not create such a failure.

If proven, add SAPDiagnose(action="activation_log") or an equivalent bounded read. Preserve message class/number, severity, object and source references; attach a log reference after activation failure when available. Do not automatically repeat activation just to obtain a log. Keep “log unavailable,” “no entries” and “activation successful” separate. Main’s existing table/index activation and state-verification work is related but does not close the log gap.

Batch syntax checks

FEAT-69 is a small, useful follow-up. Extend the shared syntax-check path to accept a bounded object set, returning checked/failed/not-checked status per object and explicit aggregate completeness. Verify the multi-object ADT contract before relying on a batch request; otherwise use bounded calls. A successful empty response must not become “all objects passed.” Reuse the current syntax handler.

How to adapt the remaining workflows

Timeline and transport review: package existing evidence

Use SAPRead(type="VERSIONS"), SAPRead(action="diff") and SAPTransport(action="diff") to produce a single report: object, author, request/task, before/after references, changed hunks and validation results. Keep the existing selectionMethod and baselineStatus visible. A latest-revision fallback must not be presented as an exact transport diff. A human-readable export or client panel is sufficient; the server already computes the comparisons. Transport selection logic.

Service inspection: a narrow first step

Use service-binding metadata to identify the OData endpoint, inspect metadata/entity sets, and run explicitly selected bounded GET requests. Reuse the existing host-relative path protections and selected SAP identity. Return schema, status, sample size and timing separately. A successful metadata request does not prove a write operation works. Keep test writes, cleanup and CSRF handling in explicitly authorized workflows rather than a generic unrestricted tester. SAP’s Swagger launcher is a useful UX reference, not a requirement to embed a new browser-based API console.

Action discovery: describe known operations before adding execution

Build a filtered catalog from the current action policy, tool/type registries and discovered capabilities. It can say that this object supports checking, activation or a known refactoring, and state the relevant prerequisites. Unknown actions advertised by SAP should not become callable merely because their metadata says they exist. Every executable action needs an operation classification, scopes, write ceiling, package/transport checks where applicable, input validation, result verification and audit behavior. Keep the current intent tools; do not add a long list of one-tool-per-endpoint wrappers.

Editing and explanations: preserve ARC-1’s existing strengths

Keep source changes synchronous within lock→read/modify→unlock and preserve scope/package gates. Review the pending anchored-edit proposal on its own correctness merits, including duplicate anchors, stale source, no-op behavior and concurrent edits. The SAP tool reference says unsaved editor coding can be read; reproducing that requires a client buffer bridge and version identity, not a change to the backend source reader. For explanations, compose existing dependency context with the caller’s model and source citations. SAP’s documented explanation/documentation tools have separate service and cost conditions, so do not treat them as free backend APIs for an ARC-1 dependency. SAP MCP tool reference.

ATC exemptions: request preparation before mutation

Start only after a customer confirms the relevant classic/cloud workflow. Read the latest finding, discover permitted approvers, and prepare justification, validity and object references. A request is a state-changing operation even though it does not change application source; map it explicitly into ARC-1’s authorization policy. Preserve approval as a separate governed step. Do not automatically exempt findings to make a CI result green. Prove transport and CHKE behavior on the relevant backend before adding a common abstraction.

Source index and remaining uncertainty

  • SAP: 1.2 release notes, MCP access restrictions, MCP tool catalog, SQL notebooks, ABAP feeds. These pages were read live for this review.
  • ARC-1: published v1.5.2, pinned main snapshot, current idea roadmap, target authorization readiness, security invariants.
  • Implementation references: VS Code Notebook API; MCP Apps overview for a possible later renderer. No MCP Apps integration is assumed present in ARC-1.

Confidence is high for registry/handler presence, released-versus-main distinctions and existing policy mechanisms. It is medium for the proposed client implementation effort. Activation-log, exemption and SRVC wire contracts remain research items; this assessment does not claim they were exercised against SAP. Exact production permissions and deployed ARC-1 versions remain outside this review.

Recommendation: adopt the reusable investigation workflow and clearer controls. Preserve ARC-1’s centrally enforced, client-independent execution model.
