2. Transport diff: what works, and where it needs attention

The foundation is good. ARC-1 matches request and task IDs, skips active/inactive pseudo-versions when selecting a historical baseline, skips contiguous same-transport snapshots, accepts predecessors with no transport ID, rolls CTS components into logical objects and selects relevant class includes. It keeps unsupported object types as inventory and distinguishes exact attribution from fallback selection. These are substantial advantages for review.

The current source has nine revision-feed routes: PROG, CLAS, INTF, FUNC, INCL, DDLS, DCLS, BDEF and SRVD. Read/write support for another object type does not automatically mean historical transport diff support. TABL, DDLX, DOMA, DTEL, MSAG and function-group container/include coverage need separate treatment.

A. A selected class include can disappear after a 404

Fix first diffPart() returns null when a non-main class include’s history returns 404. This is reasonable only for a speculative include that genuinely does not exist. The same behavior applies when CTS explicitly lists that include. If another part succeeds, the missing include is filtered out and the object has no inventory warning.

Reproduced: a class with CTS entries for METH and CINC/CCIMP, a readable main history and a 404 implementations history returns only the main part. The current test covers “every part fails”; it does not cover this mixed result.

Change: pass the reason a part was selected into the reader. A CTS-selected part must produce a visible unavailable or not-supported row on 404. A speculative part may be marked not-present only when there is enough evidence of absence. A 404 alone does not establish deletion, lack of changes or lack of authorization.

Your benefit: a review cannot quietly lose a local helper or test include. Acceptance: expected parts equal returned parts plus explicitly classified omissions.

B. Missing attribution can be reported as “not changed”

Fix first For a whole-class R3TR entry, suppressUntouchedParts() blanks every successful fallback part if any sibling has an exact match. It changes its counts to zero and adds “not changed by this transport.”

Reproduced: main has exact transport attribution; implementations has two different sources but blank transport IDs. The implementations row retains prior-revision-unverified, yet its hunks and counts disappear and the note claims no change. The contradictory evidence labels make human and AI interpretation harder.

Change: distinguish unattributed from unchanged. Keep the candidate diff available in a separate section, preserve its statistics and explain that it cannot be assigned to this request. Collapse boilerplate visually when appropriate; do not replace uncertainty with certainty. A sibling’s successful attribution is not proof about another part.

Your benefit: less noise without losing potentially relevant changes. A reviewer can choose to inspect uncertain parts; the tool cannot make that choice invisibly.

C. Text-pool changes are reduced to a source comparison

Add coverage warning immediately LIMU REPT entries are rolled into PROG or CLAS. The output no longer retains the component inventory, and the engine only compares source parts. A changed text symbol, selection text or heading can therefore produce a plain “no source change between the selected revisions.” That statement can be true for source while the transport still changes user-facing text.

Reproduced: a REPT-only transport with identical source produces a zero-line source diff and no text-pool coverage warning.

Change now: preserve component kinds and emit text-pool: not-reviewed. Investigate next: historical text-pool reads, language handling, missing translations and serialization. ARC-1’s existing current text-element reader is useful infrastructure, but comparing today’s text to historical source does not create a historical text diff.

Your benefit: classic ABAP changes become reviewable without pretending that “zero code lines” means “zero functional change.” This also establishes a pattern for Dictionary metadata and Customizing inventory.

D. An undated active revision can get the wrong baseline status

Fix the evidence classification Sorting puts undated revisions last. A matching active pseudo-version 00000 with no timestamp can be selected there, leaving no predecessor in the forward walk even when released version 00002 exists. The later check compares numeric version numbers; no released number is less than zero, so it returns no-prior-snapshot.

Reproduced: [dated released 00002 from another request, undated active 00000 for the reviewed request] yields current 00000, previous null, no-prior-snapshot. The engine then compares the source against empty text. This is a synthetic edge case; I have not observed that exact feed on your server.

Change: handle active/inactive states separately from numbered historical snapshots. Never infer chronology from pseudo-version numbers. Where ordering is unresolved, return ambiguity. Also remove documentation that equates “no prior snapshot” with “created here”: missing or retained history alone cannot prove creation.

Your benefit: fewer misleading full-file additions and false “new object” summaries.

E. Review intent and source state are currently mixed

Make the contract explicit When an inactive draft 99999 and active state 00000 both match the request, the newest timestamp can select 99999. The existing tests intentionally accept this. That is useful for reviewing work in progress, but it is not the same as reviewing the currently active source or a released snapshot.

Reproduced: a newer inactive draft wins and is labelled prior-revision, with only the numeric revision identifying it as inactive. The transport status is not passed into the per-object selector.

Change: offer clearly defined modes: released for attributable historical snapshots, active for the current activated state of an open request, and draft for saved inactive work. Preserve the current behavior under an explicitly documented legacy/latest-work mode if needed for compatibility. Return sourceState, comparison intent and activation status. Missing history in released mode must not silently become today’s active source.

Keep the existing release guard. SAP’s activation model requires objects to be activated before release; a draft review does not establish release readiness. Checks must state which source state they examined.

F. SAP 1.2 has a test-transport revision rule worth adopting

Verify on live history, then implement The installed SAP 1.2 client parses adtcore:isTestTransport on revision entries. Its transport diff excludes flagged entries unless they belong to the transport being reviewed. ARC-1’s revision parser does not retain this flag and its selector cannot apply the rule.

Reproduced: with requested revision 00003, flagged intermediate revision 00002 and earlier regular revision 00001, ARC-1 drops the flag and chooses 00002 as baseline. Depending on the workflow, that can show only the delta since a test transport instead of the intended regular correction boundary.

Change: preserve the flag, retain an auditable list of excluded revisions and define an explicit test-transport policy. Keep a flagged revision when it is the requested transport; normalize request/task identities consistently. Do not guess from transport descriptions, and do not treat every transport of copies as equivalent to this metadata flag.

Live acceptance: a normal request with an intervening flagged snapshot; the flagged request reviewed directly; missing flag; request/task attribution. Until those cases are captured, call this a verified client contract and parser gap, not a verified production incident.

G. Pagination is ordered, but it does not freeze the review

Needed for multi-page review artifacts Sorting prevents errors caused by SAP returning objects in a different order. Each offset call still re-reads the request. If objects are added or removed between calls, the index shifts: [A,B,C,D], first page [A,B], remove A, then offset 2 yields [D] and skips C. Source content can also change without any change to the inventory.

Change: include a fingerprint of the normalized object/component inventory, request status, target and comparison mode. Require it for continuation; reject/restart on drift. Bind continuation to the authenticated user, server target and request. Hash the exact source evidence used for a saved review. A stable inventory does not prove stable source; reread relevant state/hash evidence before calling an active review current. Do not imply an atomic SAP snapshot where none exists.

Your benefit: a review of 80 objects can demonstrate which 80 were examined, rather than merely concatenate pages taken at different times.

H. A line cap is not a complete workload or response budget

Add bounded collection before scaling ARC-1 caps a page at 40 logical objects and each displayed diff at 400 lines. The full sources and patch are processed before this cap. At the current maximum, 40 whole classes × 5 parts × up to 3 reads is roughly 600 ADT reads, plus the transport read. The shared semaphore bounds concurrent requests, not total bytes, queued work or cumulative duration.

Reproduced: one changed line containing 300,000 characters returns a 300,154-character diff without diffTruncated. This is a stress fixture, not evidence that such ABAP lines are common. Ordinary large multi-object patches can also become expensive. The existing full added/removed counts remain useful even when display hunks are capped.

Change: add a byte budget, per-source bound, total review/request deadline and cancellable work queue. Start with summary/statistics and load selected hunks on demand. Cap at whole-hunk boundaries where possible, declare omitted content and provide bounded continuation. Use the diff library’s bounded-work options if supported by the installed version; do not assume the network semaphore protects the diff calculation.

Your benefit: predictable MCP responses, lower context use and fewer stalled reviews. Measure output bytes, backend requests, p95 latency and process memory on representative transports.

I. History completeness, deletions and ownership need targeted research

The revision parser drops continuation metadata and converts parse failure to an empty history. A synthetic rel="next" is ignored. I have not established that the relevant SAP version feeds paginate, so this is a contract check, not a demonstrated live omission. Validate the feed shape and mark unexpected XML separately from a valid empty history.

Deletion evidence, historical text/metadata, function-group include ownership, transport-of-copies baselines and simultaneous method changes in different requests require dedicated fixtures. A full class main-source diff may be broader than the particular METH component recorded in CTS; retain those component identities and verify cross-request behavior before attributing every hunk to one request. Current unsupported inventory is preferable to invented history.

A source-system correction diff also does not establish what is deployed in QAS/PRD. Target drift needs a separately labelled cross-system comparison using authorized read-only connections and a proven baseline.

3. What the improved transport product should return

A reviewable evidence bundle: a compact machine-readable result, plus a human-readable report with a changed-object list, source hunks, review findings and coverage. Put uncertain or unsupported areas beside the conclusion. Keep deterministic facts separate from the AI’s interpretation.

Deterministic evidence

  • System/client, request and task IDs, request type/status, retrieval time and comparison mode.
  • Raw CTS component inventory and logical-object mapping; inventory fingerprint.
  • Expected, attempted and returned source parts.
  • Revision IDs/URIs, transport attribution, source state, timestamps, source hashes and skipped-revision reasons.
  • Exact, unattributed, unavailable, unsupported, not-present, cosmetic and changed classifications.
  • Complete/truncated flags and bounded paths to remaining evidence.

Human and AI review

  • What behavior changed, with object/part/hunk references.
  • Which tests and checks actually ran, against what source state and when.
  • Risks and suggested tests, each linked to evidence.
  • Open questions for text, metadata, Customizing and missing history.
  • Separate check failure, blocked check, execution error, not-run and stale result.
  • No automatic “safe to release” verdict inferred from an empty diff or a successful tool response.

Proposed contract, not a current API:

Use mutually exclusive coverage categories and publish the denominator. A percentage of “objects with any readable main source” is not a percentage of fully reviewed changes. Preserve the existing baselineStatus and selectionMethod fields for compatibility; add explicit coverage and source-state dimensions.

Compose existing tools: SAPTransport.diff → relevant SAPContext dependency analysis → syntax/ATC/ABAP Unit as requested → report. Run deeper analysis on changed or uncertain objects, not every dependency by default. Reuse current CI outputs and policies. The new work is evidence collection and presentation, not a replacement ATC engine. A read-only review does not require transport release rights.

5. Diagnostics and policy: turn dead ends into explainable next steps

Feed schemas and typed filters

Recommended: promote FEAT-74 from a small diagnostics enhancement to the foundation of a focused incident workflow. Ask “TIME_OUT dumps for this object/package in this time window,” retrieve relevant details, then correlate with known changed objects and versions. Correlation should produce candidates, not an assertion that a particular transport caused the error.

The roadmap already records live SAP_BASIS 816 evidence for /sap/bc/adt/feeds: typed attributes, operators and query depth. That is stronger than guessing a raw filter string, but it is not proof that every attribute exists on your 758 system.

Implementation: expose discovered schema for approved feed families; accept a small typed filter tree; validate attribute/operator/type/depth against that target’s schema; compile using a grammar-aware serializer; enforce row/time/page budgets; keep existing user/from/to parameters working. Group equivalent runtime errors and fetch detailed chapters only for relevant samples. Cache schema by target and relevant capability/auth context, not incident content across users.

Important edge cases: quotes and delimiters, time-zone normalization, missing attributes on 758, 403 versus an empty result, cap saturation and more than one page of incidents sharing a timestamp. Preserve current dump-pagination safeguards. Do not fix a saturated query by silently broadening it.

Benefit to you: repeatable triage and less irrelevant tool output; a natural consulting workflow of incident → evidence → candidate cause → proposed fix → verification. Measure time to the first relevant dump, backend calls and bytes returned, rather than how many new filter fields exist.

Dictionary activation logs: the investigation is now narrower

New evidence from installed SAP 1.2: DdicActivationLogSupport resolves an object link with relation http://www.sap.com/adt/relations/ddic/activationlog and media type application/vnd.sap.adt.logs+xml. The language-server activation extension follows that URI with GET and parses a hierarchical log. This is a distinct path from probing /activation/runs.

The previous roadmap’s “not a simple GET endpoint” description is therefore incomplete as a description of the current client. It should be revised after backend verification: discover the object’s activation-log relation and validate the read contract and freshness. This research did not establish that the link is present on your 2023 objects.

First probe: read metadata for an existing DDIC object with known activation history; locate the relation; follow only a canonical same-system ADT link with the advertised media type; record the object/type, severity hierarchy and available timestamps/run identity. Try an object without a log and a restricted user. Start with existing logs; a controlled failure fixture is a later test if the existing evidence is insufficient.

Minimal implementation: SAPDiagnose(action="activation_log", type, name) as a proposed read action; hierarchical entries with bounded depth, count and bytes; severity and object references; explicit unavailable/unsupported/denied outcomes. After an activation failure, optionally offer this diagnostic read. Never reactivate merely to obtain a log.

Freshness is the acceptance gate: an accessible log may belong to an earlier activation. If the backend supplies no reliable run/timestamp correlation, label it “latest available log; not correlated to this attempt.” Include retrieval time separately. Do not tell an agent that stale log text explains its current failure.

Your benefit: the RAP/DDIC generation workflow can stop guessing after a failure and explain the next concrete repair. It is especially useful for tables, structures, dependent types and CDS; exact availability still depends on backend metadata.

Policy explanation, using the policy ARC-1 already enforces

Recommended: add a read-only explanation for the current caller and proposed action. Example: “Source reads are allowed; SQL is blocked by the server’s free-SQL setting; editing this object is blocked because its actual package is outside the allowed subtree.” That helps administrators configure a pilot and helps an agent avoid repeated doomed calls.

Reuse: ACTION_POLICY, dispatch checks, safety configuration, real-package resolution and target authorization. Refactor decision evaluation to produce structured reasons if needed; do not implement an independent approximation for the UI. Keep final authorization at execution time.

How this can become paid value

Transport review service: offer a bounded review of a customer’s transport set, with behavior changes, evidence, coverage and test recommendations. The deliverable is the review package; ARC-1 makes it repeatable. Do not market a full release certification when metadata or baselines remain unreviewed.

Incident investigation service: combine filtered runtime evidence, relevant source history and a reusable notebook. The customer receives the diagnosis, its limits and a reproducible verification procedure. That is more valuable than a transcript of tool calls.

Enablement and supported deployment: package policy explanation, verified capabilities and a few useful notebook/review templates into onboarding. Since ARC-1 is MIT-licensed, the practical commercial hypothesis is supported operation, integration, training and expert deliverables; feature work alone does not establish willingness to pay.

Illustrative capacity calculation, not measured ROI: 30 transport reviews/month × 15 minutes saved = 7.5 hours/month; 12 investigations × 20 minutes saved = 4 hours/month; 4 onboarding/support cases × 30 minutes saved = 2 hours/month. That is 13.5 hours/month under those assumptions. Replace the assumptions with pilot measurements and your actual utilization/value of time. Freed capacity is not automatically additional revenue.

Pilot measurements

  • Median time to a reviewer-ready transport summary; correction/rework rate after human review.
  • Coverage by component type and source part; unknown, unavailable and unsupported rates.
  • False “unchanged” or “complete” classifications in the adversarial fixture set: target zero.
  • Backend requests, response bytes, p95 review latency and memory on small and large transports.
  • Time to a relevant incident and the number of irrelevant dump pages fetched.
  • Notebook rerun rate and whether a colleague can repeat the investigation without asking the author.
  • Onboarding time and repeated denied operations before and after policy explanations.

A strong public story: “Review what changed, see what could not be reviewed, and rerun the checks.” Demonstrate your real class main/include changes and the flight notebook. Publish measured improvements only after the pilot. The credibility comes from visible evidence and honest coverage.

Static inspection of the installed class metadata/bytecode established the revision flag, filter, whitespace option and activation-log lookup/GET. No claim is made that each behavior first appeared in 1.2, or that the same backend contract is available on every release.

SAP comparison corrections: 1.2 exposes an ignoreWhitespace option, default false. The old comparison’s blanket whitespace limitation should not be carried forward. Its inspected revision-selection methods still use a single correction-number match and an immediate predecessor rule; ARC-1’s task matching and same-transport walk remain valuable. Avoid a blanket “ARC-1 is more accurate than SAP” claim without an end-to-end comparative corpus.

Tests: 181 tests passed across transport-diff, source-diff, revision-feed transport parsing and transport handler test files, using Node 24.19.0. These are existing unit tests with mocked backends, including mock mutation tests; they did not change SAP. Eight additional synthetic probes called unmodified current source. Their outputs reproduce code behavior, not the incidence of those edge cases in customer systems.

Live reads: five read-only MCP calls: demo request A4HK906371; class main and implementations histories; explicit 00001→00002 diffs for both. These confirm the historical demo changes on the connected SAP system. No new SAP objects, transports, writes, activations or releases were performed.

Unverified: live occurrence of the new edge-case fixtures, 758 activation-log availability/freshness, 758 extended feed attributes, historical text/metadata contracts, revision-feed continuation and customer ROI. The currently connected tool surface does not expose upstream SAPTransport.diff; the two live diffs therefore validate underlying source-history reads, not the whole new engine through that connector.
